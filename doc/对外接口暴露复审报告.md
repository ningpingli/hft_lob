# 对外接口暴露复审报告

> 整改状态（2026-08-20）：对外 facade 已按领域收敛到各子包 `__init__.py`；不再
> 增设 `hft_lob.api` 二次转发层。MLP 按用户确认归入 baseline，不属于 models API。
> 下文建议保留为复审时快照。

## 1. 结论

当前公开接口存在明显的“内部接口暴露过多、主链路接口暴露不足”问题。

建议将接口分为三级：

1. **稳定应用 API**：用户运行实验需要直接调用的入口；
2. **扩展 API**：开发新模型、数据源或评估器时需要的契约；
3. **内部实现**：hash、manifest I/O、collate、单项指标、callback builder 等，不承诺兼容。

目前各包没有遵守这三级边界：`preprocessing`、`models`、`systems` 的 `__all__`
接近“把能 import 的都导出”，而根包只暴露 `main`，无法完成一次程序化实验。

## 2. 包级检查

### 2.1 `hft_lob` 根包

当前只导出：

```python
__all__ = ["main"]
```

问题：

- `__version__` 已定义但未加入 `__all__`；
- 稳定程序化入口完全缺失；
- 用户必须了解内部包结构才能执行 prepare/walk-forward；
- 直接在根包导出全部对象又会导致导入 torch/lightning/polars 的重依赖。

建议根包保持轻量：

```python
__all__ = ["__version__", "main"]
```

程序化接口直接按领域从 `hft_lob.configs/preprocessing/systems` 导入，避免新增
`hft_lob.api` 二次转发层。核心公开对象包括：

```python
__all__ = [
    "ExperimentConfig",
    "PreparedDataset",
    "PredictionArtifact",
    "EvaluationReport",
    "FoldResult",
    "WalkForwardReport",
    "load_config",
    "prepare_dataset",
    "run_walk_forward",
]
```

这是当前最明显的“应该暴露但没有暴露”。

### 2.2 `hft_lob.configs`

当前没有任何导出，甚至没有 `__all__`。

应至少公开：

```python
__all__ = [
    "ExperimentConfig",
    "TaskConfig",
    "DataConfig",
    "CleaningConfig",
    "TargetConfig",
    "SessionConfig",
    "WindowConfig",
    "FeatureConfig",
    "NormalizationConfig",
    "LoaderConfig",
    "ModelConfig",
    "BaselineConfig",
    "TrainingConfig",
    "EvaluationConfig",
    "SplitConfig",
]
```

`RAW_FEATURE_COLUMNS` 可作为扩展契约公开；`PRICE_COLUMNS` 更偏内部质量检查，不建议公开。

`load_config()` 现在放在 `utils`，从领域语义上应移动或重新导出到 `configs`。

### 2.3 `hft_lob.models`

当前严重过度暴露：

- GatedAxialAttention；
- SinusoidalPositionalEmbedding；
- BiN、BL_layer、TABL_layer；
- BiN_BTABL、BiN_CTABL；
- 大量非 MVP 且未实现模型。

这些属于模型内部 layer 或 experimental 实现，不应进入稳定 `__all__`。

稳定公开建议只保留：

```python
__all__ = ["build_model", "CNN1", "DeepLOB", "MLP"]
```

如果希望强制所有调用方经过工厂，甚至可以只公开 `build_model`。

发现一个实际缺失：

- 配置允许并提示 `model.name="mlp"`；
- 已存在 `models/MLP/mlp.py`；
- 但 `models.__init__` 没有导入/导出 MLP；
- `build_model()` 也没有 `if name == "mlp"` 分支。

这是 P0 接口断点，不只是暴露风格问题。

非 MVP 模型建议迁移到 `hft_lob.experimental.models`，不要出现在主工厂错误提示和稳定 facade 中。

### 2.4 `hft_lob.baselines`

当前公开 concrete model、runner、protocol、工厂和特征下标 helper。

过度公开：

- `volume_feature_indices()` 是工厂内部实现；
- `ZeroBaseline/ImbalanceBaseline/RidgeBaseline` 如果不支持用户单独构造，也无需公开；
- `BaselineRunner` 由 `run_walk_forward` 内部编排时，不应作为应用 API。

建议扩展 API 只保留：

```python
__all__ = ["BASELINE_NAMES", "BaselineModel", "build_baseline"]
```

如果 baseline 不允许外部插件，则进一步只保留 `build_baseline`。

### 2.5 `hft_lob.preprocessing`

这是当前暴露最严重的包。公开了：

- DataCleaner、FeatureTransformer、LabelTransformer；
- manifest build/read/write；
- raw/config/version hash；
- split helper；
- normalizer 实现和 fit service；
- session 中间对象。

对普通调用方，唯一必要入口其实是：

```python
__all__ = [
    "PreparedDataset",
    "WalkForwardPlan",
    "QualityReport",
    "prepare_dataset",
]
```

扩展数据处理时可从专门模块导入 `SessionSegment`、`DataCleaner`、
`FeatureTransformer`、`LabelTransformer`，但不应由包级 facade 承诺稳定。

建议改为内部符号或内部模块：

- `raw_file_hash`；
- `stable_config_hash`；
- `dataset_version/feature_version/label_version`；
- `build_manifest/read_manifest/write_manifest`；
- `chronological_split/walk_forward_folds`；
- `label_column`；
- `fit_train_only_normalizer`。

这些均由 `prepare_dataset/run_walk_forward` 消费，用户不应手工拼装另一条流水线。

### 2.6 `hft_lob.datasets`

当前公开：LOBBatch、LOBWindowDataset、SampleMeta。

建议：

- `LOBBatch`、`SampleMeta` 是跨模块数据契约，应该公开；
- `LOBWindowDataset` 是 DataModule 的实现细节，普通用户不需要；
- 如果支持自定义 DataModule/Dataset，它可以作为扩展 API 保留，但不进入稳定应用 facade。

推荐包级：

```python
__all__ = ["LOBBatch", "SampleMeta"]
```

### 2.7 `hft_lob.systems`

当前同时公开高层结果对象和几乎所有底层函数，接口面积过大：

- 单项 mae/rmse/ic/rank_ic；
- icir/positive ratio；
- prediction bins/bootstrap；
- build_loss；
- git_commit；
- LOBDataModule/StageFiles；
- LOBLightningModule；
- artifact writer；
- walk-forward 高层入口。

稳定应用 API 应只保留：

```python
__all__ = [
    "PredictionArtifact",
    "EvaluationReport",
    "FoldResult",
    "WalkForwardReport",
    "run_walk_forward",
]
```

扩展 API 可额外公开：

```python
"LOBBatch", "LOBLightningModule", "build_evaluation_report"
```

不建议从 `systems` facade 暴露：

- `mae/rmse/ts_ic/...`：属于 metrics 模块内部或专家接口；
- `git_commit`：artifact 内部 helper；
- `StageFiles/LOBDataModule`：fold runner 内部装配；
- `build_loss`：Lightning wrapper 内部工厂；
- `save_prediction_artifact`：若 artifact 负责自行保存，应改为对象方法或独立 artifact store。

当前 `systems` 名称本身过于宽泛。长期建议拆成 `training`、`evaluation`、
`artifacts`，但 MVP 阶段可先缩小 `__all__`。

### 2.8 `hft_lob.utils`

当前 utils facade 暴露所有 helper。应用用户通常不应依赖 `utils`，否则内部重构困难。

建议：

- `load_config` 移到/重新导出到 `configs`；
- `set_seed` 由 run entry 内部调用；
- experiment/checkpoint/logger helper 均留在各自模块，不加入包级 `__all__`；
- `utils.__all__` 可以删除，或仅用于仓库内部，不视为稳定 API。

### 2.9 `hft_lob.train`

该模块没有 `__all__`，因此所有非下划线函数都被视为可导入：callback builder、trainer
builder、run_training、run_test、run_predict。

在统一闭环中，这些均由 `run_walk_forward` 编排，普通用户不应直接调用，否则可以绕过
fold-specific normalizer 和统一 artifact。

建议：

- 重命名为 `_build_checkpoint_callback`、`_build_trainer` 等；或
- 明确 `__all__: list[str] = []`，把它作为内部单-fold executor；
- 如果需要扩展 API，只暴露一个 `run_fold()`，不要暴露六个可自由组合的零件。

## 3. 应该暴露但当前缺失的接口

按优先级排序：

### P0

1. `configs/preprocessing/systems` 的稳定领域 facade；
2. `configs.ExperimentConfig` 与 `configs.load_config`；
3. `models.MLP` 及 `build_model("mlp")` 分支；
4. 包根 `__version__`；
5. 一个可持久化/加载 `PreparedDataset` 的接口，否则 prepare 和后续独立进程执行仍会断开；
6. `PredictionArtifact` 的读取接口。目前只有 save，没有 load，离线 evaluate 无法从 parquet 恢复；
7. `EvaluationReport` 的保存/读取接口，否则评估结果只能留在内存。

### P1

1. 扩展模型的 Protocol/ABC，例如 `ReturnForecaster`，目前只有文档约定；
2. artifact store 或 registry 接口；
3. `RunManifest`；
4. 配置校验入口 `validate_config()`；
5. 稳定异常类型。

## 4. 推荐的最终公开面

### 应用层

```python
from hft_lob.configs import load_config
from hft_lob.preprocessing import PreparedDataset, prepare_dataset
from hft_lob.systems import WalkForwardReport, run_walk_forward
```

### 模型扩展层

```python
from hft_lob.models import build_model
from hft_lob.contracts import ReturnForecaster, LOBBatch
```

### 数据扩展层

```python
from hft_lob.contracts import SessionSegment, SampleMeta
```

其余对象通过具体模块导入，不纳入稳定兼容承诺。

## 5. 推荐整改顺序

1. 修复 MLP 注册断点；
2. 完善 configs/preprocessing/systems 的领域 facade；
3. 补 `configs.__all__` 并迁移/重导出 `load_config`；
4. 收缩 models/preprocessing/systems/baselines/datasets 的 `__all__`；
5. 将 train helper 私有化；
6. 增加 PreparedDataset、PredictionArtifact、EvaluationReport 的 load/save；
7. 再考虑 contracts 包、异常层和 experimental 模型迁移。

完成前四项后，对外 API 才具有清晰、可维护的边界。
