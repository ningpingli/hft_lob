# 接口框架数据与参数流复审报告

> 整改状态（2026-08-20）：本报告识别的统一闭环 P0 项已完成接口整改。当前唯一
> 主链路为 `PreparedDataset → WalkForwardPlan → fold normalizer → LOBBatch →
> model/baseline → PredictionArtifact → EvaluationReport → FoldResult`。本文后续问题
> 描述保留作为整改依据。

## 1. 复审结论

本次按当前仓库实际接口重新追踪完整链路，不沿用首次报告的已整改结论。

**结论：主数据链路轮廓已经清楚，但仍存在 8 个 P0 断流点、7 个 P1 参数多源或冗余问题。目前不宜开始大规模实现。**

当前理想链路应为：

```text
YAML
  → ExperimentConfig
  → raw column mapping
  → CleanDayResult(SessionSegment AM/PM)
  → FeatureTransformer
  → LabelTransformer
  → session parquet + manifest
  → chronological / walk-forward plan
  → StageFiles
  → train-only normalizer state
  → Dataset / Batch
  → model or baseline
  → Lightning training / baseline runner
  → PredictionArtifact
  → EvaluationReport
```

目前真正能够在接口上首尾相接的部分主要是：

- YAML 与 `ExperimentConfig` 的字段大体对应；
- raw mapping → Cleaner → 单 session 数据边界；
- Feature/Label → 单 session processed 文件的方向明确；
- Dataset → DataLoader → `LOBLightningModule` 的基本方向明确；
- 模型已统一为纯 `nn.Module`；
- prediction metadata、metrics 和 artifact 概念已建立。

但以下接口仍无法由上游自然驱动下游。

## 2. P0：数据或参数流断裂

### P0-01：walk-forward 只有 fold 生成器，没有执行链路

`SplitConfig.walk_forward=True`，也有 `walk_forward_folds()`，但：

- `PipelineResult` 只返回单个 `ChronologicalSplit`；
- `StageFiles` 只表示一组 train/val/test；
- `run_training()`、`run_test()` 不接收 fold；
- 没有 `WalkForwardPlan`、`FoldRunResult` 或跨 fold 汇总入口；
- CLI stage 中没有 walk-forward。

因此配置打开 walk-forward 后，没有任何接口负责消费这个参数。

**建议：**增加 `WalkForwardPlan(folds, dataset_version)` 和 `run_walk_forward(plan, config) -> WalkForwardReport`；每个 fold 创建独立 normalizer、checkpoint、prediction artifact 和 evaluation report。

### P0-02：baseline 模块是孤立分支

已存在 `build_baseline()` 和四类 baseline，但当前：

- `main.py`、`train.py`、`LOBLightningModule` 均未引用 baseline；
- 没有 baseline runner；
- 没有 baseline prediction artifact；
- 没有 baseline 与主模型共用的比较报告；
- `BaselineModel.fit()` 与 Lightning 训练方式不一致，MLP 既是 `nn.Module` 又声明自行 `fit()`，训练职责再次分叉。

**建议：**Zero/Imbalance/Ridge 使用 `BaselineRunner.fit/predict`；MLP 应作为普通 `nn.Module` 走 `LOBLightningModule`，不应自行实现 `fit()`。所有输出统一为 `PredictionArtifact`，再进入同一个 evaluator。

### P0-03：DataModule 缓存生命周期与 normalizer 拟合顺序冲突

`prepare_data()` 声称在有 `cache_dir` 时构建并保存 train/val/test Dataset；但 train-only normalizer 只能在 `setup()` 中读取 training split 后拟合。Lightning 生命周期是 `prepare_data()` 在 `setup()` 之前，因此缓存 Dataset 时 normalizer 尚不存在。

可能产生：

- 缓存未归一化 Dataset；
- setup 后加载缓存却无法注入 normalizer；
- 缓存 normalizer 与当前 split/config 不一致。

**建议：**删除整个 Dataset `.pt` 缓存接口。processed parquet 本身已是缓存层；如确有性能需求，只缓存文件索引，且 key 必须包含 dataset/fold/window/feature/normalizer 版本。

### P0-04：normalizer 的 fit 输入与 DataModule 持有的数据不匹配

`TrainOnlyNormalizer.fit()` 接收 `list[pl.DataFrame]`，DataModule 持有的是 `StageFiles` 文件路径，而 Dataset 才负责读取 parquet。DataModule 若自行读取 DataFrame，会与 Dataset 文件读取/cache 逻辑重复；若从 Dataset 获取，则 Dataset 没有暴露训练帧或统计量接口。

**建议：**增加独立 `fit_normalizer(training_files, feature_cols) -> NormalizerState` 服务，由 DataModule 调用；采用流式 parquet 统计，不构造 Dataset。Dataset 只消费冻结状态。

### P0-05：dataset version 生成后没有被实验配置固定

`run_pipeline()` 返回 `dataset_version`，但 `ExperimentConfig` 没有 `dataset_version` 字段；`resolve_stage_files()` 反而从 manifest 根目录选择“最新数据集”。这使训练运行无法明确固定数据版本，恢复训练时也可能读到另一个最新版本。

**建议：**增加 `data.dataset_version: str | None`。数据处理完成后将实际版本写入 RunManifest；训练/恢复必须显式解析该版本，禁止以“最新目录”作为可复现实验接口。

### P0-06：新 EvaluationReport 没有进入训练和测试接口

已增加 `build_evaluation_report()`，但：

- `LOBLightningModule` 文档仍只描述旧 `evaluate/evaluate_by_day`；
- `run_test()` 返回 `list[dict[str, float]]`；
- `run_predict()` 返回 `list[Tensor]`；
- 没有接口把 test metadata 送入 `EvaluationReport`；
- `EvaluationConfig.metrics/report_daily` 没有传给 `build_evaluation_report()`。

**建议：**`run_test() -> EvaluationReport`；`run_predict() -> PredictionArtifact`；`LOBLightningModule.on_test_epoch_end()` 只生成 prediction records，统一 evaluator 在训练模块外执行，避免 Lightning hook 同时计算、保存和发布结果。

### P0-07：block bootstrap 缺少日期/session 边界

`block_bootstrap_confidence_interval(preds, targets, ...)` 没有 trade_date 或 session_id。即使使用连续块，也可能从一天尾部跨到下一天，或跨 AM/PM，重新引入虚假的时间连续性。

**建议：**接口接收 `PredictionRecord` 或至少 `trade_dates/session_ids`，只允许在同一 session 内抽块，再按日或 fold 聚合。

### P0-08：Dataset target shape 与模型输出契约不一致

Dataset 声明标签是“标量 float32”；默认 collate 后通常为 `[B]`。模型统一输出 `[B,1]`。损失若直接计算可能发生广播，甚至得到 `[B,B]` 的错误结果。

**建议：**Dataset 返回 `y: Tensor[1]`，collate 后严格为 `[B,1]`；定义强类型 `LOBBatch(features[B,1,T,F], targets[B,1], metadata)`，训练步骤拒绝其他 shape。

## 3. P1：参数多源、职责重叠与冗余模块

### P1-01：DataModule 工厂仍绕过强类型配置

`train.build_datamodule(general, data_cfg, loader_cfg)` 使用三个 `dict[str, Any]`，但 `LOBDataModule` 已直接接收 `ExperimentConfig`。该工厂既重复又损失类型信息。

**建议：**删除 `train.build_datamodule`，直接 `LOBDataModule(config, stage_files=...)`。

### P1-02：随机种子有三个来源

同时存在：

- `ExperimentConfig.seed`；
- `TrainingConfig.seed`；
- `LoaderConfig.seed`。

三者默认相同，但没有优先级和派生规则。修改其中一个会造成“全局可复现”语义不明确。

**建议：**只保留根 `seed`；worker、sampler、bootstrap 等通过稳定命名空间派生，例如 `derive_seed(root_seed, "dataloader")`。

### P1-03：`max_ffill_gap_seconds` 放错配置层

该参数属于清洗策略，却放在 `NormalizationConfig`。Cleaner 构造时需要从 normalization 段取清洗参数，造成跨层依赖。

**建议：**新增 `CleaningConfig`，包含 duplicate policy、max ffill gap、单边 mid policy、质量阈值等；NormalizationConfig 只保留归一化策略。

### P1-04：特征数量存在三个来源

当前来源包括：

- `ExperimentConfig.feature_count` 根据配置推导；
- `FeatureTransformer.feature_columns()`；
- `ModelConfig.num_features` 可手工覆盖。

它们可能不一致，特别是派生特征被过滤、重复或未来带参数时。

**建议：**Feature pipeline 输出唯一 `FeatureSchema(names, version)`；Dataset 和模型工厂都从该 schema 取 `num_features`。删除 `ModelConfig.num_features` 手工覆盖。

### P1-05：SampleMeta dataclass 与实际 meta dict 重复

定义了 `SampleMeta`，但 `__getitem__` 返回 `dict[str, object]`；而且 dataclass 不含 bid1、ask1、spread，实际 dict 又需要这些字段。`_collate` 再把 dict 转为 dict-of-lists，类型约束完全丢失。

**建议：**补全一个唯一的 `SampleMeta`，Dataset 返回它；`LOBBatch.metadata` 使用 `tuple[SampleMeta, ...]`。Artifact writer 直接消费该类型。

### P1-06：指标层存在两套日级接口

`evaluate_by_day()` 返回聚合 dict，`daily_metric_records()` 返回逐日记录，`build_evaluation_report()` 又同时构建二者。前两个若作为公共 API 长期保留，会形成多条计算路径和结果不一致风险。

**建议：**公共入口只保留 `build_evaluation_report()`；基础 metric 函数可保留，`evaluate_by_day()` 和 `daily_metric_records()` 降为内部函数。

### P1-07：过多非 MVP 模型扩大无效接口面积

需求明确不应让 10+ 模型成为第一期工作，但模型工厂注册了 CNN2、Transformer、iTransformer、LobTransformer、AxialLOB、DLA、TABL、HLOB 等大量未实现模型。它们带来不同输入 shape 和构造参数，却没有独立 model contract。

**建议：**MVP 工厂只注册 CNN1、DeepLOB、MLP；其他模型移动到 `experimental/`，不进入稳定 `__all__` 和主工厂，完成契约后再注册。

## 4. 其他一致性问题

### 4.1 CLI 与流水线阶段不一致

- `VALID_STAGES` 中有 `dataset_preparation`，但 pipeline 已经完成 processed + manifest，DataModule 又负责 Dataset 构造，该阶段没有明确 owner；
- walk-forward、baseline comparison 不在 stage 中；
- `main()` docstring 参数与无参签名不一致；
- 文档引用 `load_experiment_config`，实际函数叫 `load_config`。

建议 CLI 收敛为：

```text
prepare-data
train-fold / walk-forward
evaluate
predict-offline
```

### 4.2 checkpoint monitor 名称可能断开

callback 默认监控 `val_ic`，指标正式名称是 `ts_ic`。如果 LightningModule 实际记录 `val_ts_ic`，默认 callback 永远找不到 `val_ic`。

建议把 monitor 放入 TrainingConfig，并使用受约束的指标 key，例如 `val/ts_ic`。

### 4.3 offline predict 与 artifact 契约冲突

`run_predict()` 默认写 `predictions.pt`，而研究主接口要求完整 metadata parquet。该接口会绕过 `save_prediction_artifact()`。

建议删除 `output_path="predictions.pt"`，统一返回 `PredictionArtifact` 并由 artifact writer 写 parquet。

### 4.4 causal normalization 是可选但不可执行的接口

YAML 注释写“causal 待接入”，配置类型又允许 `mode="causal"`。这属于“可配置但无消费者”的孤立参数。

建议 MVP 暂时只允许 `train_only`；causal 完整接入后再开放配置值。

### 4.5 WindowConfig 硬编码 3 秒

`history_seconds` 使用 `history_snapshots * 3`，没有消费 `DataConfig.snapshot_interval_seconds`，形成两个频率来源。

建议把该计算放到 ExperimentConfig：由 window 和 data 两段共同推导，或删除该便捷属性。

## 5. 推荐的收敛后主接口

```python
@dataclass(frozen=True)
class PreparedDataset:
    dataset_version: str
    feature_schema: FeatureSchema
    manifest_path: Path
    split_plan: WalkForwardPlan

@dataclass(frozen=True)
class LOBBatch:
    features: Tensor       # [B, 1, T, F]
    targets: Tensor        # [B, 1]
    metadata: tuple[SampleMeta, ...]

@dataclass(frozen=True)
class FoldResult:
    fold_index: int
    normalizer_state: Mapping[str, object]
    checkpoint_path: Path | None
    predictions_path: Path
    evaluation: EvaluationReport

def prepare_dataset(config: ExperimentConfig) -> PreparedDataset: ...

def run_walk_forward(
    dataset: PreparedDataset,
    config: ExperimentConfig,
) -> tuple[FoldResult, ...]: ...

def evaluate_predictions(
    artifact: PredictionArtifact,
    config: EvaluationConfig,
) -> EvaluationReport: ...
```

主原则：

1. 数据处理只输出 `PreparedDataset`；
2. dataset version 必须显式传递，不选择“最新”；
3. 每个 fold 单独拟合 normalizer；
4. 模型和 baseline 最终都输出同一种 prediction artifact；
5. evaluator 只消费 artifact，不关心预测来自哪种模型；
6. `EvaluationReport` 是唯一对外评估结果。

## 6. 建议整改顺序

1. 先定义 `PreparedDataset / WalkForwardPlan / LOBBatch / PredictionArtifact / FoldResult`；
2. 修复 Dataset target shape 和 SampleMeta；
3. 删除 Dataset `.pt` 缓存，补齐 normalizer fitting service；
4. 固定 dataset version，禁止 latest 自动选择；
5. 接通 walk-forward runner；
6. 接通 baseline runner，并让模型/baseline 共用 artifact/evaluator；
7. 让 `run_test` 返回 `EvaluationReport`，修复 bootstrap session 边界；
8. 删除重复 DataModule 工厂、重复日级指标入口和多余种子；
9. 收缩非 MVP 模型注册；
10. 最后整理 CLI 和配置校验。

完成前 7 项后，接口框架的数据与参数流才算真正闭环。
