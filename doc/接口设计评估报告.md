# HFT LOB 接口设计评估报告

## 1. 评估结论

评估对象为 `doc/需求文档.md`、`configs/experiment.yaml` 及 `src/hft_lob` 下全部公开模块、类、函数和数据契约。

**总体结论：有条件不通过，不建议立即冻结接口。**

当前设计已经形成“配置 → 预处理 → Dataset/DataModule → 模型 → 训练评估 → Artifact”的基本分层，时间锚点、session、标签容差、chronological split、train-only normalization 和 prediction artifact 等核心概念也已进入接口。但接口仍处于骨架阶段，共有 **113 处 `NotImplementedError`**；更重要的是，接口层本身存在重复职责、需求冲突和 P0 能力缺口。即使暂不考虑实现，当前签名也不足以完整表达需求文档的 MVP 验收契约。

综合评分：

| 维度 | 得分 | 结论 |
| --- | ---: | --- |
| 结构合理性 | 65/100 | 分层基本合理，但入口、模型工厂和训练抽象重复，公开边界不清 |
| 功能完整性 | 48/100 | 数据主链路覆盖较多，但 baseline、walk-forward 编排、在线推理、完整评估与 release gate 缺失 |
| 接口规范性 | 58/100 | 类型标注和 docstring 较完整，但命名、异常、枚举、输入输出 schema 和版本契约不统一 |
| **总体** | **56/100** | **整改 P0 后再冻结** |

> 说明：骨架项目允许方法未实现，因此 `NotImplementedError` 本身不等于设计错误；本报告主要判断接口是否足够清晰、完整、无冲突，并将“不可执行”作为交付成熟度风险单独记录。

## 2. 评估范围与方法

### 2.1 接口范围

- 配置接口：`ExperimentConfig` 及各子配置、YAML schema；
- 数据接口：清洗、质量报告、特征、标签、归一化、manifest、split、pipeline；
- 样本接口：`LOBWindowDataset`、`SampleMeta`、DataLoader batch；
- 模型接口：模型工厂及各模型 `forward`；
- 训练接口：Lightning wrapper、loss、metrics、trainer 编排；
- 产物接口：checkpoint、实验日志、prediction artifact；
- CLI 与未来在线推理接口。

### 2.2 判断标准

- 结构：单一职责、依赖方向、唯一入口、抽象一致性、可扩展性；
- 功能：需求覆盖、时间语义、防泄漏、可追踪、可复现、失败行为；
- 规范：命名、类型、schema、错误、版本、兼容性和可测试性。

## 3. 结构角度评估

### 3.1 合理设计

1. **主链路分层正确。** `preprocessing`、`datasets`、`systems`、`models`、`utils` 的总体职责划分符合训练系统结构；预处理不放入 DataModule 的方向合理。
2. **核心领域对象已显式化。** `ExperimentConfig`、`QualityReport`、`ChronologicalSplit`、`Fold`、`PipelineResult`、`StageFiles`、`SampleMeta` 均比无约束 `dict` 更利于静态检查和单测。
3. **Dataset 锚点契约表达清楚。** 接口明确 `X = seg[i-N+1:i+1]`、`y = target[i]`，且限制同交易日、同 session，符合需求的最高优先级约束。
4. **预处理与数据加载边界总体合理。** manifest 决定切分，DataModule 消费明确的文件清单，不移动 raw 文件，方向符合数据不可变与可追踪要求。
5. **模型训练 wrapper 的方向可取。** `LOBLightningModule` 统一 loss、metrics 和 artifact，有利于让纯模型只承担 `forward`。

### 3.2 结构问题

#### S-P0-01：存在两个不兼容的 `build_model` 公共接口（已整改）

- `hft_lob.models.build_model(config, homological_structures=...) -> nn.Module`；
- `hft_lob.train.build_model(model_name, data_features, model_params, ...) -> LightningModule`。

两者参数模型、返回类型和职责均不同，同时 `train.py` 还声称自己是“唯一允许模型 if/else 的地方”，与实际实现冲突。调用方无法判断权威入口，后续容易出现配置解释不一致。

**建议：**只保留 `hft_lob.models.build_model(config) -> nn.Module`；训练编排统一调用它，再由 `LOBLightningModule(model, config, ...)` 包装。删除或私有化 `train.build_model`。

**整改状态：**已删除 `hft_lob.train.build_model`，当前唯一模型工厂为 `hft_lob.models.build_model`。

#### S-P0-02：模型基类与训练 wrapper 抽象冲突（已整改）

各模型继承 `LightningModule`，但又由 `LOBLightningModule` 统一包装训练。纯网络应继承 `torch.nn.Module`，否则出现嵌套 LightningModule、重复 hyperparameter/checkpoint 语义，未来也可能出现 `configure_optimizers` 归属冲突。

**建议：**所有算法模型统一继承 `nn.Module`；只有 `LOBLightningModule` 继承 LightningModule。

**整改状态：**所有算法模型及内部网络层均已改为继承 `torch.nn.Module`；`LOBLightningModule` 是唯一负责训练语义的 LightningModule。

#### S-P0-03：CLI 文档与实际签名不一致

`main() -> None` 无参数，但 docstring 声明 `config_path/model_name/resume_ckpt/...` 等 Args；流程中又引用不存在的 `load_experiment_config`，实际函数名是 `load_config`。这会直接误导实现和使用者。

**建议：**`parse_args(argv: Sequence[str] | None = None) -> CLIArgs`，`main(argv: Sequence[str] | None = None) -> int`；使用一个有类型的 `CLIArgs` dataclass，并让 docstring 与签名完全一致。

#### S-P1-04：公开 API 边界过宽且不稳定

`models.__init__` 暴露 TABL 内部 layer、attention、position embedding 等实现细节；同时包根只暴露 `main`。外部用户真正需要的 `ExperimentConfig`、`run_pipeline`、`build_model`、`LOBLightningModule` 没有稳定 facade。

**建议：**定义精简的包级公共 API；内部网络层放入 `_layers` 或不加入 `__all__`。为公开 API 建立兼容性策略。

#### S-P1-05：路径普遍使用 `str`，职责和约束弱

文件/目录接口均使用 `str`，缺少 `PathLike` 兼容，也无法区分 raw、processed、manifest、artifact 路径。

**建议：**公共文件接口使用 `pathlib.Path | str`，内部立即规范为 `Path`；所有写接口明确创建父目录、覆盖策略和原子写行为。

#### S-P1-06：DataModule 同时支持 parquet 懒加载和整个 Dataset `.pt` 缓存，缓存契约不清

缓存 key 没有包含 dataset/feature/label/window/normalization 版本，可能错误复用旧缓存；“幂等”只按目标文件存在判断不足。

**建议：**定义 `DatasetCacheKey`，至少包含 dataset_version、split、feature_version、label_version、window、normalizer hash 和代码版本；不建议 pickle 整个 Dataset 作为长期接口。

## 4. 功能角度评估

### 4.1 已覆盖较好的需求

| 需求 | 接口覆盖 | 评价 |
| --- | --- | --- |
| 单股、5 档、3 秒、回归 | 配置对象已表达 | 基本合理 |
| anchor 包含当前帧 | Dataset docstring 明确 | 合理，需测试固化 |
| AM/PM session 隔离 | `SessionConfig`、Cleaner、Label、Dataset 均涉及 | 覆盖完整，需统一校验点 |
| 60 秒标签与 tolerance | `TargetConfig`、`LabelTransformer` | 合理 |
| 有界 ffill 与 stale 字段 | `NormalizationConfig`、`DataCleaner` | 概念已覆盖 |
| 日级质量报告 | `QualityReport` 字段基本齐全 | 合理 |
| train-only / causal normalization | 两类 normalizer + state API | 方向正确 |
| chronological split | `ChronologicalSplit` | 合理 |
| prediction artifact | `save_prediction_artifact` | 字段方向正确 |
| MSE/MAE/Huber | `build_loss` | 覆盖完整 |
| MAE/RMSE/TS-IC/RankIC/Direction | metrics API | 基础指标已覆盖 |

### 4.2 功能缺口与冲突

#### F-P0-01：冻结规格要求 walk-forward=true，默认配置却为 false（已整改）

需求 §16 和 §42 将 walk-forward 列为必须/冻结规格；YAML 与 `SplitConfig` 默认均为 `false`。虽然存在 `walk_forward_folds` 签名，但 `PipelineResult` 只返回单个 `ChronologicalSplit`，训练入口也没有 fold 编排、fold artifact 或聚合结果接口。

**建议：**MVP 默认改为 true；增加 `WalkForwardPlan`、`FoldResult`、`run_walk_forward(...)` 和跨 fold 汇总 artifact。若暂不实施，必须明确标记项目尚未达到 MVP。

**整改状态：**YAML 与 `SplitConfig` 的 `walk_forward` 默认值均已改为 `true`；fold 执行编排仍按后续实现阶段完成。

#### F-P0-02：MVP 必须的 baseline 接口完全缺失（已整改）

需求要求 Zero、imbalance、Linear/Ridge、轻量 MLP、CNN/DeepLOB；当前只有复杂模型接口，没有 baseline 模块、统一 `fit/predict` 协议或 baseline 对比报告。

**建议：**新增 `ForecastModel` protocol：`fit(train, val) -> Self`、`predict(batch) -> [B,1]`，或将 sklearn baseline 适配为统一 evaluator 输入；至少增加 Zero、Imbalance、Ridge、MLP 四类，并定义 `BaselineComparison`。

**整改状态：**已新增独立 `baselines` 包、`BaselineModel` 协议、Zero/Imbalance/Ridge/MLP 接口及唯一 `build_baseline` 工厂，相关参数已纳入 `BaselineConfig` 和 YAML。

#### F-P0-03：在线 inference contract 缺失

需求 §33 明确输入 ticker/timestamp/N snapshots，输出预测时间、horizon、return、model_version、data_quality；异常时返回 `NO_PREDICTION`。当前 `run_predict` 实际是离线 test 数据预测，输出默认还是 `predictions.pt`，并非在线推理接口。

**建议：**新增独立 `inference` 包：

```python
@dataclass(frozen=True)
class PredictionRequest:
    ticker: str
    anchor_timestamp: datetime
    snapshots: Sequence[LOBSnapshot]

@dataclass(frozen=True)
class PredictionResponse:
    status: Literal["OK", "NO_PREDICTION"]
    reason: NoPredictionReason | None
    prediction_timestamp: datetime
    horizon_seconds: int
    predicted_return: float | None
    model_version: str
    data_quality: DataQualityStatus
```

并复用离线清洗、特征和 normalizer state，禁止另写一套线上语义。

#### F-P0-04：评估指标不完整（已整改）

缺少需求明确要求的上涨/下跌 Precision、Recall，daily metric 明细，confidence interval，以及 prediction decile return。`evaluate_by_day` 只返回四个聚合值，无法审计每日结果；也没有 block bootstrap 接口。

**建议：**返回结构化 `EvaluationReport`，包含 overall、daily table、decile table、CI 和样本数；避免只有 `dict[str, float]`。

**整改状态：**已增加上涨/下跌 Precision 与 Recall、`DailyMetricRecord`、`PredictionBinRecord`、moving block bootstrap `ConfidenceInterval` 和统一 `EvaluationReport`，并将分桶数及 bootstrap 参数纳入实验配置。

#### F-P0-05：模型 release gate 与 baseline 对比没有接口

需求要求 Data Quality、Statistical Predictability、Temporal Stability、Economic Value 四层 Gate。当前没有 gate 输入、阈值、判定结果和失败原因 schema。

**建议：**新增 `ReleaseGateConfig`、`GateResult(status, checks, reasons, evidence_paths)`；MVP 至少实现前三层，若未进行交易评估则 Gate 4 返回 `NOT_EVALUATED`，不能默认为通过。

#### F-P0-06：数据版本不具备真正版本唯一性（已整改）

`dataset_version` 仅由 ticker、首日、末日组成；同日期范围内 raw 内容、清洗规则、feature/label/tolerance 变化都不会改变版本。`feature_version` 只记录派生特征数量，不记录名称和顺序，两个不同特征集可能同版本。

**建议：**版本使用 processing config + raw file hash 的稳定 hash，例如 `dataset_<12hex>`；manifest 保存 `raw_hash/config_hash/code_commit`。

**整改状态：**`dataset_version` 已改为由 raw 内容哈希集合和 processing config 稳定哈希生成；字段映射属于 processing config。manifest 增加对应追踪字段，`feature_version` 改为按特征名称及顺序生成，不再仅记录数量。

#### F-P0-07：原始字段契约存在拼写与命名不兼容风险（已整改）

需求原文使用 `AskPrice1/AskVolume1/.../volumn`，代码固定为 `ASKp1/ASKs1/.../volume`。规范化命名本身合理，但缺少显式 raw-to-canonical schema mapping，Cleaner 的“必需列”会让合法来源数据无法接入。

**建议：**在数据配置中显式定义 raw 到 canonical 的字段映射；兼容 `volumn -> volume` 但输出统一 `volume`，映射冲突必须报错。

**整改状态：**已在 YAML 的 `data.column_mapping` 中直接配置 raw 到 canonical 的映射，Cleaner 接收该映射；不同数据源只修改配置，不增加额外 schema 抽象。多个原始列映射到同一 canonical 字段时必须报错。

#### F-P0-08：`valid` 语义混合，容易错误丢样本（已整改）

Cleaner 的 `valid` 表示盘口/填充质量，Label 的 invalid 表示 future 匹配失败，Dataset docstring 又称“窗口内所有行必须 valid（含超容差标签）”。窗口中历史行不需要拥有有效未来标签，只有 anchor 的 target 必须有效。若把 label validity 合并到每行 `valid`，将错误删除大量本可用于 X 的历史快照。

**建议：**拆分为 `book_valid`、`feature_valid`、`target_valid`；样本条件应为 `all(window.book_valid & feature_valid) AND anchor.target_valid`。

**整改状态：**已拆分三类有效性，并将 AM/PM 从同一 DataFrame 的逻辑分组升级为独立 `SessionSegment` 物理边界。特征和标签接口一次只能处理一个 segment；processed 文件一 session 一文件，Dataset 拒绝包含多个 trade_date/session_id 的文件。split 仍按完整交易日决策。

#### F-P0-09：归一化接入契约自相矛盾（train-only 已整改）

`TrainOnlyNormalizer` 设计为变换 DataFrame；`LOBWindowDataset` 又接受 tensor mean/std 自行归一化；DataModule 文档称 `fit(train) -> transform(all)`，但 `_make_dataset` 参数仍是 mean/std。存在双重归一化或实现分叉风险。causal 模式虽在配置中可选，DataModule 明确“待接入”，因此选择该配置会形成静默不满足需求的路径。

**建议：**只保留一个归一化位置。推荐预处理后、Dataset 取样前使用 `Normalizer` protocol，并让 Dataset 只读规范数据；未支持模式在 config validation 时立即报错，不能默默跳过。

**整改状态：**train-only 已统一为 `TensorNormalizer` 单一路径：DataModule 仅从 training split 拟合并冻结状态，Dataset 是唯一应用 `transform_tensor` 的位置；已删除 DataFrame transform 及裸 `feature_mean/feature_std` 注入。causal 模式接入仍属于后续独立整改项。

#### F-P1-10：窗口时长计算硬编码 3 秒

`WindowConfig.history_seconds` 使用 `history_snapshots * 3`，没有读取 `DataConfig.snapshot_interval_seconds`。改变数据频率后配置会自相矛盾。此外 N 个等间隔快照首尾跨度严格为 `(N-1)*interval`，需求文档将 N×interval 作为名义历史长度，两种定义需明确区分。

**建议：**移除该 property，改由根配置提供 `nominal_history_seconds` 与 `window_span_seconds` 两个明确属性，并校验 frozen spec。

#### F-P1-11：prediction artifact 与 `run_predict` 输出冲突

需求和 artifact 模块规定 parquet 是主要研究接口，但 `run_predict` 默认 `predictions.pt` 且返回 `list[Tensor]`，会绕过元数据和版本字段。

**建议：**离线预测统一返回/保存 `PredictionArtifact`，默认 parquet；tensor 列表仅作为内部临时值，不作为公共 API。

#### F-P1-12：实验可复现字段不完整

目前接口涉及 experiment_id、git commit、config、seed、checkpoint，但缺少 raw hash、feature/label schema hash、Python/NumPy/PyTorch/CUDA 版本、实际 train/val/test 日期、optimizer 完整配置和环境 lock hash 的统一 run manifest。

**建议：**新增强类型 `RunManifest` 并在训练开始时写入、结束时补齐结果；配置备份不能替代运行 manifest。

#### F-P1-13：监控、市场状态分析、信号层和 latency 尚无接口

这些属于 P1，不阻塞数据预测 MVP，但当前包结构没有扩展点。建议在 P0 稳定后增加 `analysis/regimes.py`、`signal/`、`monitoring/`，避免提前塞入训练模块。

## 5. 接口规范性评估

### 5.1 命名规范

- `Complete_HCNN`、`BL_layer`、`TABL_layer` 不符合 Python 类名 PascalCase，应为 `CompleteHCNN`、`BLLayer`、`TABLLayer`；旧名可短期 alias 并标记 deprecated。
- `CNN1.__init__(num_classes=1)` 是分类遗留语义，回归应统一为 `output_dim=1`。
- `history_length`、`window_size`、`history_snapshots` 三种名称表达同一概念；统一为 `history_snapshots`。
- `ASKs/BIDs` 中 `s` 含义不直观；canonical 列建议采用 `ask_price_1`、`ask_volume_1` 等 snake_case。
- stage 同时出现 `fit/validate/test/predict` 与 `training/validation/test`；应使用枚举或 Literal，并在边界处显式转换。

### 5.2 类型与数据结构

- `dict[str, Any]`、裸 `tuple`、`dict[str, object]` 用于关键公共接口，约束不足。建议使用 dataclass、TypedDict、Protocol、Literal/Enum。
- `LOBLightningModule.training_step(batch: tuple, ...)` 应使用明确的 `Batch` 类型；模型输入 shape 应在运行时校验并给出领域错误。
- `meta: dict[str, list[object]]` 无法保证必需字段、同长度和类型；应定义 `PredictionRecord` 或 Arrow schema。
- 时间当前大量使用 `str`/`seconds`，建议规范为 timezone/交易所时区明确的 `datetime`，落盘使用 `timestamp[us, Asia/Shanghai]` 或明确的 naive exchange-local 约定。

### 5.3 参数校验

dataclass 没有 `__post_init__` 校验，以下非法配置会延迟到运行期：

- levels != 5、snapshot interval <= 0；
- horizon/tolerance/history <= 0；
- `allow_cross_session=true` 与 MVP 契约冲突；
- task_type 非 regression、output_dim != 1；
- ratio 越界或三段为空；
- model 名、loss 名、metric 名、normalization mode 非法；
- `persistent_workers=true` 但 `num_workers=0`；
- `prefetch_factor` 与 worker 配置不兼容。

**建议：**集中提供 `validate_config(config) -> None`，错误包含字段路径和合法值；配置加载不能“缺键全部默认兜底”而掩盖拼写错误，应拒绝未知字段。

### 5.4 异常规范

当前主要声明 `ValueError/FileNotFoundError/NotImplementedError`，缺少可操作的领域错误。

建议最小异常层次：

```text
HFTLOBError
├── ConfigError
├── SchemaError
├── DataQualityError
├── TemporalInvariantError
├── LeakageDetectedError
├── ArtifactSchemaError
└── UnsupportedCapabilityError
```

在线推理的数据问题不应抛通用异常，应映射为稳定的 `NoPredictionReason`（窗口不完整、stale、跨 session、异常盘口、模型/特征版本不匹配等）。

### 5.5 Schema 与兼容性

建议为以下产物定义常量 schema 和 `schema_version`：

- canonical LOB snapshot；
- processed row；
- dataset manifest；
- prediction artifact；
- run manifest；
- evaluation report。

写入时严格校验必需列、dtype、nullability、单位和时区；读取时检查 schema version，禁止凭列名猜测格式。

## 6. 建议的目标接口结构

```text
hft_lob/
├── config.py              # 强类型配置、加载、校验
├── schemas.py             # Snapshot/Batch/Artifact/Manifest schema
├── preprocessing/         # clean/features/labels/normalize/split/pipeline
├── data/                  # Dataset/DataModule，仅消费 manifest
├── models/                # 纯 nn.Module + 唯一模型工厂
```

## 8. 验收建议

接口冻结应至少满足：

- 仓库内只有一个模型工厂和一个训练 wrapper；
- 配置中不存在“可选择但未接入”的静默路径；
- requirement-to-interface matrix 的所有 P0 项均有明确 owner、输入、输出、失败行为和测试；
- synthetic golden data 可验证 anchor、午休隔离、future tolerance、有界 ffill、train-only normalization；
- 同一 raw 日期范围改变内容或配置后 dataset version 必须变化；
- baseline、CNN/DeepLOB 可通过同一 evaluation API 比较；
- walk-forward 输出逐 fold、逐日和汇总指标；
- prediction parquet、manifest、run manifest 均通过 schema 校验；
- 在线坏数据稳定返回 `NO_PREDICTION + reason`；
- ruff、mypy、pytest 均在项目声明的标准命令下通过。
